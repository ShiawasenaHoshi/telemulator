# Design: тестовый Telegram (зонтичный спек)

Дата: 2026-08-13
Статус: согласован в brainstorming; волны 1–3 сданы, вынос состоялся
Предыдущий эпик остался в приватном репозитории происхождения и сюда не переехал.

Это **зонтичный** документ и устав продукта: конечная картина, границы, фасады, модель данных, философия полноты Bot API и нарезка на волны. На него опирается планирование волны 4. Пошагового плана реализации здесь нет: каждая волна — отдельный цикл spec → plan → implementation.

Написан до выноса, когда эмулятор ещё жил пакетом `tgmock/` внутри репозитория другого проекта, и говорит об этом в настоящем времени. Сам тот проект не назван: он частный, и публиковать его имя — не дело этого продукта.

## 1. Цель

Нужен тестовый Telegram, в котором можно завести сто пользователей и несколько ботов без SIM, BotFather и настоящих аккаунтов.

- Любой бот (aiogram, grammY, Telegraf, …) смотрит на фейковый Bot API как на `api.telegram.org`: сменил базовый URL — живой.
- Человек сидит в веб-клиенте или в автотесте (`press` / `send`) за любого пользователя.
- Люди пишут людям, ботам, позже — в группы и каналы.
- Состояние либо живёт на диске (песочница на дни ручной приёмки), либо поднимается чистым / из снимка (CI).

Критерий идеи (не одной волны): бот проекта-происхождения и любой следующий бот прогоняются против этой сети без реальных аккаунтов; руками можно открыть клиент «как Telegram Web» и жать те же кнопки, что жмёт pytest.

## 2. Границы

### Входит в картину продукта

- Ядро сети: пользователи, боты, чаты, сообщения, участники.
- Три фасада к одной правде: Bot API, User API, Admin API.
- Drop-in Bot API: polling и webhook, канонические типы и ошибки.
- Программный клиент человека и веб-клиент с разметкой как у Telegram Web.
- Режимы хранения: память, SQLite-файл, снимок.
- Группы, супергруппы, каналы.
- Режим живых лимитов Bot API по FAQ Telegram: выключен по умолчанию, включается по заказу инстанса/теста (рассылки).
- Каталог методов/типов, снятый с официальной доки (чтобы 404 отличать «дыра эмулятора» от опечатки). Реализации по каталогу не генерируем.
- Журнал вызовов Bot API и debug-консоль (волна 2): request/response, нереализованные методы. Не отдельный продукт.
- Вынос в отдельный репозиторий (волна 1.5, сделано).

### Не входит никогда

- MTProto и подключение официальных приложений (Desktop, iOS, Android, нефоркнутый Telegram Web).
- Молчаливый `ok: true` на неизвестный метод Bot API.
- Пиксель-форк Telegram Web K / Web A (GPL-комбайн на GramJS).
- Вех «все 185 методов Bot API реализованы». Полнота растёт по падениям реальных ботов (404 + журнал Admin). Telegram сам добавляет методы каждый релиз — «закрыть API» нельзя.

### Не входит в этот документ

- Пошаговый план реализации, полный список методов API, макеты экранов. Это планы волн.

## 3. Происхождение и стек

Эмулятор рос не как отдельный продукт с первого дня, а внутри репозитория частного проекта — на его живом боте, с уже существующими `TELEGRAM_API_BASE` и compose-сервисом. Дешёвый стенд был важнее чистоты: каждый шаг ядра проверялся настоящим ботом в тот же день.

Дисциплина, которая позволила вынести пакет, а не переписать его:

- Домен сети, Bot API, User API, Admin API и хранилище разделены внутри пакета с самого начала.
- Боевые пакеты проекта-происхождения эмулятор не импортируют.
- Специфика того проекта (обходчик экранов, стоп-листы, дампы состояний) живёт в его тестах, не в ядре эмулятора.

Вынос состоялся после волны 3 (см. волну 1.5 в §11): отдельный репозиторий, пакет и Docker-образ, проект-происхождение подключает их как зависимость тестов и по-прежнему смотрит `TELEGRAM_API_BASE`.

Стек ядра: Python / FastAPI. Веб-клиент — отдельное SPA.

Готовый продукт не форкаем и не подменяем ядром. Ближайший аналог — [laraXgram/Simula](https://github.com/laraXgram/Simula) (Rust + веб-клиент, prerelease). Остальные — моки двери бота без сети людей, faker «все методы ок», LLM-юзеры или моки библиотеки без HTTP. Подробности и что именно забираем — в §13.

## 4. Архитектура

Одна правда — сеть. Бот и человек не пишут в разные базы: `sendMessage` бота и «нажал кнопку» пользователя — одно сообщение в одном чате.

```
любой бот  ── Bot API  ──┐
веб / тест ── User API ──┼──► ядро сети ──► память | SQLite
сиды / CLI ── Admin API ─┘
```

| Фасад | Кто говорит | Контракт |
|---|---|---|
| **Bot API** | любой бот | drop-in `https://<host>/bot<token>/<method>`, polling и webhook, типы и ошибки [Bot API](https://core.telegram.org/bots/api) |
| **User API** | веб-клиент и автотест | сессия человека. HTTP для действий (отправить, нажать, список чатов, лента); SSE — события «в чате появилось/изменилось сообщение». Этого протокола у Telegram нет: он заменяет MTProto, не копирует его |
| **Admin API** | сиды, CLI, кнопки в клиенте | создать пользователя/бота (токен), открыть диалог, снимок, сброс, очередь 429/403, журнал нереализованных методов |

Настоящий MTProto нет. Telegram Desktop сюда не подключается. Человек ходит только в User API.

Хранилище — режим, не вилка кода. Одно ядро, два бэкенда: память (тест с нуля) и файл SQLite (песочница переживает рестарт). Снимок — выгрузка/загрузка состояния сети. E2e проекта-происхождения по умолчанию память; демо-стенд может включить файл.

`UserClient` остаётся фасадом для тестов. Снаружи `press` / `send` как сейчас; внутри — User API. В процессе pytest допускается короткий путь без HTTP при том же контракте. Long-poll и подтверждение offset для бота — живой HTTP, как в e2e-спеке 2026-08-03. Ожидание «хендлер закончился» живёт в `UserClient`, не в ядре: ядро трактует offset как Telegram (апдейт забрали).

## 5. Модель данных

Источник правды — [Available types](https://core.telegram.org/bots/api#available-types). Параллельных «карточек пользователя» нет. В ядре лежат те же JSON-объекты, что бот видит в ответе Telegram. Необязательные поля, как в доке, не отдаём, пока они нерелевантны.

### Сущности API

| Тип | Роль |
|---|---|
| `User` | человек и бот — один тип, различает `is_bot`. Обязательные: `id`, `is_bot`, `first_name`. Опционально: `last_name`, `username`, `language_code`, `is_premium`. Поля только для `getMe` заполняются у бота. |
| `Chat` | `id`, `type` ∈ `private` \| `group` \| `supergroup` \| `channel`. Для private — `first_name` / `last_name` / `username` собеседника; для остальных — `title`. |
| `ChatFullInfo` | ответ `getChat`. |
| `Message` | лента. Обязательные: `message_id`, `date`, `chat`. Остальное — по виду сообщения. Схема целиком из доки; какие поля живые — определяется волной. |
| `Update` | очередь бота. Ровно одно опциональное поле, как требует дока. |
| `CallbackQuery` | `id`, `from`, `chat_instance`; плюс `message` и `data`. Inline-режим и games — позже. |
| Вложенные | `MessageEntity`, `InlineKeyboardMarkup` / `InlineKeyboardButton`, `ReplyKeyboardMarkup` / `ReplyKeyboardRemove`, `PhotoSize`, `Document`, `File`, `UserProfilePhotos`, `ChatMember*` (волна 3). |

Идентификаторы как в доке: до 52 бит; у group/supergroup/channel — отрицательные. Токен бота — формат `123456:ABC…`, чтобы фреймворки не спотыкались.

### Служебное, чего в Bot API нет

Токен бота, сессии User API, байты файлов, конфиг webhook, очередь инъекций 429/403, снимок сети, журнал вызовов нереализованных методов.

Reply-клавиатура в `Message` не хранится — она «висит» у клиента. Держим как состояние пары (user × chat), чтобы веб-клиент и `press` видели то же, что живой Telegram.

User API отдаёт те же `User` / `Chat` / `Message`, не вторую схему. Admin API создаёт `User` (`is_bot: false|true`) и выдаёт токен, если бот. BotFather как бот внутри сети не эмулируем: кнопки «новый пользователь / новый бот» в клиенте — оболочка над Admin API.

## 6. Потоки

Снаружи бот не должен отличить нас от `api.telegram.org` на реализованных методах. Внутри — одна каноническая лента чата, не распределённые копии сообщений Telegram.

### Нажатие inline-кнопки

1. Человек (веб или `UserClient`) вызывает User API: нажать кнопку с `callback_data` на этом `message_id`.
2. Ядро проверяет, что сообщение есть и кнопка на нём живая. Собирает `CallbackQuery` по доке, кладёт `Update` в очередь каждого бота, которому событие адресовано (правила адресации — из доки: private; в группах — privacy mode и права, волна 3).
3. Бот забирает апдейт: `getUpdates` или webhook POST с тем же JSON.
4. Бот отвечает Bot API: `answerCallbackQuery`, `editMessageText`, `sendMessage`, … Ядро меняет `Message` на месте или дописывает новый.
5. Подписчики User API видят ту же ленту. Старые inline-кнопки в истории остаются живыми, пока сообщение не удалили — как в Telegram.

Webhook и polling на одном боте не живут вместе. `setWebhook` выключает `getUpdates`.

### Человек → человек

Шагов Bot API нет. Сообщение сразу в ленте обоих. Бот не в курсе, пока его нет в чате.

### Бот пишет первым

Чат для бота существует после `/start` пользователя. Иначе — каноническая ошибка Bot API, не создание чата молча.

### Что не Telegram, а тестовый сахар

Помечать явно, не выдавать за Bot API:

- Admin API «открыть диалог» без `/start` — для сидов.
- Снимок сети.
- Ожидание `press()` по ack оффсета: сервер Telegram считает offset «бот забрал апдейт», а не «бизнес-логика закончилась». Совпадает с обработкой, только если фреймворк не берёт следующий `getUpdates`, пока хендлер не вернулся (aiogram, `handle_as_tasks=False`). Это контракт харнесса.

## 7. Ошибки

Ошибки бота — как в Bot API: тело `{ok: false, error_code, description}`, HTTP-статус совпадает с `error_code`. У 429 — `parameters.retry_after`.

| Ситуация | Ответ боту |
|---|---|
| Нет токена / кривой токен | 401 `Unauthorized` |
| Неизвестный метод | 404 `Not Found` — как у Telegram, не 501 |
| Несуществующий `chat_id` | 400 `Bad Request: chat not found` |
| Пользователь не начинал диалог | 403 `Forbidden: bot can't initiate conversation with a user` |
| Пользователь заблокировал бота | 403 `Forbidden: bot was blocked by the user`; в private — ещё `my_chat_member`, когда этот апдейт включён |
| `edit` несуществующего сообщения | 400 `Bad Request: message to edit not found` |
| Два `getUpdates` на один токен | 409 `Conflict: terminated by other getUpdates request; make sure that only one bot instance is running` |
| Инъекция лимита (Admin) | 429 с `retry_after` |
| Живой лимит (режим FAQ включён) | 429 с `retry_after`, как у Telegram |

`description` — канонические строки Telegram, чтобы фреймворки и ретраи вели себя как в бою.

Неизвестный метод **не** возвращаем боту как 501. Факт «метод не реализован» пишем в лог и в Admin API (счётчик и последние вызовы). Тест эмулятора может проверять этот журнал. Так drop-in снаружи не ломается, дыра эмулятора не молчит.

429 по умолчанию сами не генерируем: обычный CI и e2e проекта-происхождения идут без лимитов, иначе полоса флаки.

**Режим живых лимитов** — именованный профиль, включается флагом инстанса / Admin API / фикстурой теста (рассылки). Числа — из [Bots FAQ](https://core.telegram.org/bots/faq#broadcasting-to-users) на дату профиля, не «угаданные». Параметры в конфиге, чтобы обновить «актуальные» лимиты без переписывания ядра:

| Профиль | Правило |
|---|---|
| `telegram-faq` (волна 1) | ~1 сообщение/с в один чат; ~30 сообщений/с суммарно в разные чаты (рассылка) |
| `telegram-faq` + группы (волна 3) | плюс 20 сообщений/мин в одну группу |
| `telegram-paid-broadcasts` (по задаче) | 1000/с, как paid broadcasts в BotFather. Не в волне 1 |

Инъекция одного 429 через Admin остаётся: точечный тест ретрая, без включения всего профиля.

Неотвеченный `answerCallbackQuery` — спиннер в веб-клиенте, как в доке. Поздний ответ — `400 Bad Request: query is too old and response timeout expired or query ID is invalid`.

Webhook в волне 1: `setWebhook` / `deleteWebhook` / `getWebhookInfo`; непустой URL выключает `getUpdates` (409, как в доке); апдейт уходит POST JSON на URL. Ретраи на не-2xx и заполнение `WebhookInfo.last_error_*` — в том же плане волны 1, если дёшево, иначе сразу следом; e2e проекта-происхождения остаётся на polling.

Таймаут `press()` — не молчаливый fail: текущий экран, последние вызовы Bot API, очередь апдейтов, журнал нереализованных методов.

Admin-методы (снимок, инъекция 429, открытие диалога без `/start`) в Bot API не существуют и не маскируются под него.

## 8. Веб-клиент

Ещё один клиент User API, не клон Telegram и не замена MTProto.

**Разметка** — как у Telegram Web: колонка чатов слева, шапка, лента пузырей, композитор снизу, inline-кнопки под сообщением, reply-клавиатура над полем ввода, переключатель аккаунтов. Ориентир — открытые Web K / Web A как референс вёрстки. Код этих репозиториев не форкаем: они на MTProto/GramJS и GPL-3.0.

**Умеет (волна 2, в рамках ядра волны 1):** сессия пользователя; создать человека / бота через Admin API; список чатов и лента `Message` (текст, фото, документ, подпись); нажатие inline (спиннер до `answerCallbackQuery`); URL-кнопки; reply-клавиатура и ввод, включая `/start`; несколько сессий — переписка людей видна с обеих сторон.

**Не умеет, пока волна явно не попросит:** группы/каналы (волна 3); звонки, секретные чаты, «печатает», прочитано, стикер-паки, реакции, пустые экраны живого клиента без данных в User API.

Клиент не знает ни Bot API, ни базы проекта-происхождения. В CI Python-покрытия не входит. Автотесты ходят в User API напрямую. Смоук волны 2: открыть клиент, нажать кнопку, лента совпадает с тем, что видит `UserClient`.

Имя и логотип Telegram на вынесенном продукте не ставим.

## 9. Тесты и стык с проектом-потребителем

Три слоя.

1. **Контракт эмулятора** — собственные тесты: типы как в доке, 404 на неизвестный метод плюс запись в Admin, 401/403/400/409, offset, edit, callback, снимок, память vs SQLite. Фикстуры — канонические JSON, не урезанные «наши» объекты.
2. **Клиент человека** — `UserClient` через User API. `press` / `send` сохраняют смысл. Обходчики экранов и стоп-листы потребителя — в его тестах, не здесь.
3. **E2e потребителя** — бот с настоящим polling на `TELEGRAM_API_BASE`. Существующие сценарии не переписываются пачкой: фасад `UserClient` стабилен. Compose-полоса потребителя поднимает эмулятор сервисом.

Playwright по веб-клиенту — по желанию в волне 2, не блокер ядра.

## 10. Полнота Bot API

Bot API 10.2 (июль 2026) — **185 методов** и **~388 типов**. На момент написания эмулятор закрывал **12** методов, которых хватало первому потребителю: `getUpdates`, `getMe`, `sendMessage` / `sendPhoto` / `sendDocument`, `editMessageText` / `editMessageReplyMarkup`, `answerCallbackQuery`, `getFile`, `getUserProfilePhotos`, `setWebhook` / `deleteWebhook`.

Оценка «сделать всё заранее» (один разработчик, уже знакомый с ядром):

| Что | Срок | Зачем / почему нет |
|---|---|---|
| Заглушки `ok: true` на все 185 | 3–5 дней | Бесполезно: бот падает на пустых типах, тесты зелёные враньём |
| Честное ядро (сообщения, файлы, polling, ошибки) — уже волна 1 | заложено в волну 1 | То, чем живут почти все боты |
| Группы/каналы и админ-методы (~20) | волна 3 | Нужна модель участников |
| Остальные кластеры «как живой Telegram» (стикеры, платежи/Stars, инлайн, форумы, business, stories, rich/ephemeral) | **6–12 недель** | И сразу отстаём: каждый релиз Telegram добавляет методы (10.1→10.2 = +5 методов, +29 типов) |
| Один кластер «по падению» (404 в журнале Admin) | **0.5–2 дня** | Платим только за то, что реальный бот вызвал |

Поэтому веха «API закрыт» не ставится. Неизвестный метод — 404 боту и запись в Admin; следующий кластер берём, когда в это упёрлись.

Каталог с [core.telegram.org/bots/api](https://core.telegram.org/bots/api) (как скрейпер Simula) — это **список имён и схем**, не генератор заглушек. В волне 1 достаточно закоммиченного снимка имён методов плюс пометки в журнале: «нет хендлера» / «имени нет в каталоге». Скрипт обновления снимка — если дёшево; полноценный кодоген типов как у Simula не блокер ядра. Faker и zero-value `ok: true` на весь каталог запрещены.

## 11. Волны

| Волна | Что | Критерий готовности |
|---|---|---|
| **1. Ядро** | Сеть на типах Bot API; private человек–бот и человек–человек; Bot/User/Admin API; канонические ошибки; каталог методов с официальной доки; журнал вызовов и нереализованных методов; память и SQLite; снимок; polling полностью; webhook POST без обязательных ретраев; движок лимитов с профилем `telegram-faq` (1/с чат, 30/с рассылка), по умолчанию выключен. `UserClient` и e2e потребителя зелёные без переписывания сценариев. | `/start` → меню → inline; два человека переписываются; бот не видит чужой private; 404 на дырявый метод виден в Admin как «нет хендлера»; с включённым профилем рассылка >30/с даёт 429; `pytest -m e2e` зелёный (без профиля) |

| **2. ## 12. Связь с прототипом, из которого выросли

Уже есть и остаётся точкой опоры: HTTP-сервер на loopback, `getMe` / `getUpdates` / send / edit / callback / файлы, `UserClient.press`, инъекция 429/403, маршрутизация по токену, compose-образ.

Уйдёт из ядра: `BotState` как единственная модель; админ-ручки вида `/admin/{token}/updates`, заточенные под compose-смоук (переедут на Admin API); 501 с именем метода в ответе боту (замена — 404 + журнал Admin). Ожидание ack остаётся в `UserClient`, ядро его не выдаёт за Bot API.

Волна 1 считается успешной только если существующие e2e потребителя зелёные. Регресс этой полосы не обменивается на «правильную архитектуру сети».
